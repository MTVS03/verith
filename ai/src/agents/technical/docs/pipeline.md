# 7. 파이프라인 (Pipeline)

`docs/pipeline.md`

가격/기술적 분석 에이전트(②번)의 내부 구조를 5개 그림으로 설명한다. **보는 순서가 곧 이해 순서다:** 전체 구조 → 정상 흐름 → 멀티 타임프레임 상세 → 장애·검증 → 예외·분기·루프.

> **색 규칙은 모든 그림에서 공통** — 보라는 LLM, 청록은 코드다.

전체 구조·저장·슈퍼바이저 관계는 `architecture.md`가 담당한다. 이 문서는 **그 구조가 어떤 순서로 도는가**를 그림 단위로 서술한다.

---

## 1. 전체 구조 — A~E층 파이프라인

`assets/pipeline_ae_layers.png`

에이전트 내부 전체를 한 장으로 조망한다. 상위 Top Supervisor가 "LG에너지솔루션 기술적 분석 해줘" 같은 변형된 질의를 넘기면, 이 에이전트 안의 Technical Supervisor가 흐름을 돌려 최종 리포트(JSON)를 만들어 상위로 반환한다.

**안쪽 흐름:**
```
질문 안전 정규화·분석 포커스 정리(LLM) → 데이터수집·지표계산(코드) → 국면분류(코드)
→ 종합·신뢰도·리스크(코드) → 차트생성(코드) → 국면해석·리포트(LLM)
```

regime 라벨도 confidence 점수도 전부 코드가 확정하고, 마지막 LLM(10번)은 그 값을 문장으로 풀기만 한다. LLM이 숫자나 라벨을 스스로 만들지 않으므로 **환각이 들어올 틈이 구조적으로 막혀 있다.**

**바깥 두 층:**
- **E·하네스(resilience):** 전체 흐름을 감싸 KIS 호출 실패나 데이터 부족을 받아낸다.
- **D·관측(observability):** 전 구간에 trace를 깔고 오른쪽 검증 3층으로 각 노드를 검사한다. 특히 ③(LLM 라벨 왜곡 검증)이 이번 설계에서 새로 생긴 가장 중요한 검증이다.

**메모리/검색 층(C)이 없는 이유:** 빠뜨린 게 아니라, 이 에이전트는 숫자 계산 기반이라 의미검색·GraphRAG가 필요 없어 의도적으로 제외했다. 부재가 설명 포인트다.

## 2. 정상 흐름 — 성공 경로 (노드 10개)

`assets/pipeline_success.png`

모든 것이 정상일 때 노드 10개가 흐르는 순서를 빠짐없이 펼친 것이다. 그림 1이 "무엇이 있는가"라면, 이 그림은 "어떤 순서로 도는가"다.

**LLM은 3곳뿐(보라):** 1.질문 안전 정규화, 2.분석 포커스 정리, 10.국면해석·리포트. 나머지 7개는 전부 결정론적 코드다.

**신규 노드 3개(굵은 테두리):** 5.국면분류, 7.신뢰도계산, 8.리스크관찰점. 이번 기획에서 에이전트 역할을 강화하며 추가됐다. 예전엔 "지표 5개 + 점수"만 냈지만, 이제 국면 라벨·신뢰도·리스크 관찰점까지 만든다.

**노드 4·5가 멀티 타임프레임으로 갱신됨(노란 테두리):** 노드 4는 일봉 기반 지표를 계산하고(구현상 confidence·risk가 소비하는 IndicatorBundle 스칼라 묶음), 노드 5가 일봉 국면 판정에 더해 **주봉·월봉 추세를 계산하고 상위 타임프레임으로 보정**한다(주/월 추세 계산은 노드 5 책임 — `regime/multiframe.py`, `trace_schema.md §9`). 상세는 그림 3에서 다룬다.

**의존성 순서:** 국면분류(5)는 원지표에서 바로 나오므로 종합(6) 앞에, 신뢰도(7)는 `signal_score`를 입력받으므로 종합 뒤에 둔다. 차트(9)는 리포트 직전에 두어 그 시점 데이터를 최종 스냅샷으로 굳힌다.

**가장 중요한 원칙:** 10번 LLM은 regime·score·confidence·risk를 만들지 않는다. 코드가 확정한 라벨·수치를 문장으로 풀기만 한다. regime과 confidence가 코드에 있다는 것이 veriθ 신뢰성 설계의 핵심이다.

> **노드 어댑터 구현 규약(3~9번):** 각 노드는 `services`·`indicators`·`regime`·`synthesis`·`charts` 모듈을 호출하는 **얇은 wrapper**이며 계산 로직을 재구현하지 않는다. 모듈의 **로컬 dataclass/리스트를 그대로 반환**하고 최종 `contracts.*` 조립은 하지 않는다(계약 조립·전역 state는 supervisor 단계). `indicator_calculate`는 confidence·risk가 소비하는 최신 지표 스칼라 묶음(IndicatorBundle)을 만들고, `regime`·`signal_aggregate`·`chart_generate`는 OHLCV에서 지표를 각자 내부 재계산한다(self-contained). 상세: `implementation_plan.md §3`.

## 3. 노드 4·5 상세 — 멀티 타임프레임

`assets/node4_5_multiframe.png`

노드 4·5가 어떻게 일봉을 넘어 주봉·월봉까지 보는지를 확대한 그림이다. 일봉만으로 "지금 국면"을 말하면 큰 흐름을 놓치기 때문에, 상위 타임프레임을 함께 본다.

**타임프레임마다 역할이 다르다.** 일/주/월을 똑같이 계산하지 않는다.

- **일봉(주력):** 기본 5개 지표 계산. 실제 신호와 `signal_score`가 여기서 나온다. 단 데이터 부족으로 특정 지표 계산이 불가능하면 계산 가능한 지표만 쓰고 남은 지표로 가중치를 재정규화한다(코드가 결정).
- **주봉(중기):** 추세 방향 + 주요 지지저항. "지금 국면이 초입이냐 중반이냐"의 맥락.
- **월봉(대세):** 추세 방향만. "큰 흐름에서 상승이냐 하락이냐".

**일봉·주봉·월봉을 KIS에서 각각 조회한다.** 같은 `inquire-daily-itemchartprice`에 `FID_PERIOD_DIV_CODE`만 D/W/M으로 바꿔 부른다. 세 타임프레임 모두 KIS 원본 시세라, 상위 추세·차트가 전부 실제 데이터에 근거한다.

**노드 5는 "보정"이 된다:** ① 일봉으로 1차 국면 판정 → ② 주/월 추세로 보정 → ③ 정합/역행 플래그와 함께 최종 regime 확정. 예를 들어 "일봉 과열 + 월봉 상승"이면 `final_regime`은 여전히 `overheated`이고, `alignment_flag`는 `neutral`로 둔다(과열은 중립 국면이라 방향성 판정을 하지 않는다). 상위 추세가 상승이라는 사실은 `regime_context`에만 설명한다.

**여전히 결정론이다.** 보정도 규칙 테이블로 하지 LLM이 감으로 하지 않는다. "일봉 라벨 + 상위 추세 → 최종 라벨" 매핑이 코드에 있어, 검증 ②로 그대로 테스트된다.

## 4. 장애·검증 — D·E층 실패 분기

`assets/pipeline_de_failure.png`

문제가 생겼을 때 어떻게 되는지, 그리고 결과를 어떻게 검증하는지를 보여준다. 왼쪽 성공 줄기는 압축하고, 오른쪽에 E가 받아내는 실패 지점을, 아래에 D의 검증 3층을 배치했다.

**E·하네스 — 실패를 받는 층:**
- **E1. 재시도·백오프:** 데이터수집에서 KIS 호출이 실패하면 재시도·백오프를 거치고, 그래도 안 되면 stale 캐시로 폴백한다. 흐름이 죽지 않는다.
- **E2. 데이터부족 가드:** 국면분류에서 봉이 부족하면 regime을 억지로 만들지 않고 "판단 불가"로 정직하게 빠진다. 데이터가 없으면 없다고 말하는 것이 honest scoping의 핵심이다.

**D·관측 — 결과를 검증하는 층:** 전 구간에 trace를 깔고, 아래 3개 검증이 각 노드를 검사한다.
- **① 계산 정확성(기존):** RSI·이동평균이 라이브러리 계산과 일치하는지. 노드 4·5를 mock 단위테스트로 검사.
- **② regime 규칙(신규):** "정배열 + RSI 72"가 정말 "과열"로 나오는지. 결정론 규칙이므로 입력→라벨 테스트 케이스로 검증. **멀티 타임프레임 보정 규칙도 여기서 함께 검증된다.**
- **③ LLM 라벨 왜곡 검증(신규·최중요):** 코드가 준 라벨과 LLM 출력 문장 속 라벨이 일치하는지. regime이 "횡보"인데 LLM이 "상승 전환"이라 쓰면 환각이다. 노드 10을 trajectory eval로 검사한다. **"LLM을 썼지만 검증으로 가뒀다"를 실제로 증명하는 지점이다.**

**읽는 법:** 바깥 회색 점선(E)은 실패를 받는 층, 초록 점선(D)은 검증하는 층이다. A(오케스트레이션)는 흐름의 화살표·분기로 이미 표현돼 있고, C(메모리)는 없는 것이 정답이다.

## 5. 예외·분기·루프 — 최종 흐름

`assets/pipeline_branches.png`

성공 경로에 예외·분기·루프를 실제 흐름으로 얹은 최종 버전이다. 가운데 세로 줄기가 정상 흐름(직진), 오른쪽으로 빠지는 것이 예외 처리다. 되돌이 화살표는 루프를 뜻한다.

**루프는 딱 2곳, 둘 다 상한이 있다:**
- 데이터수집에서 KIS 호출이 실패하면 **재시도 루프** — 최대 3회, 1·2·4초 백오프.
- 국면 해석 후 검증 ③이 실패하면 **재생성 루프** — 단 1회, 라벨을 강제 주입해 재검증.

두 루프 모두 횟수 제한이 있어 **무한 루프가 구조적으로 불가능**하다. 시퀀스 다이어그램의 `loop [최대 3회]`와 맞물린다.

**모든 예외 경로가 안전하게 착지한다.** 억지 판단이나 환각으로 끝나는 경로가 하나도 없다.
- KIS 재시도 소진 시: D 실패+stale daily 있으면 `stale_cache`("최신 시세 미반영"), D 실패+캐시 없으면 `data_limited`(환각 안 채움), W/M 실패+stale 있으면 stale 상위 타임프레임 사용, W/M 실패+캐시 없으면 해당 추세 `unavailable`로 두고 일봉 기준 분석 계속
- 봉 수 부족 → regime "판단 불가"(E2)
- 검증 재생성 후에도 실패 → 템플릿 문장으로 폴백

**regime "판단 불가"는 신호 종합을 건너뛴다.** 판단불가 박스가 6~8번(종합·신뢰도·리스크)을 스킵하고 바로 차트로 빠진다. 국면을 못 정했으면 신호 종합도 하지 않는다 — "이 종목은 지금 판단 못 함"으로 정직하게 빠지는 흐름이다.
