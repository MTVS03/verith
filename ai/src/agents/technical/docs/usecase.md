# 9. 유스케이스 (UseCase)

`docs/usecase.md`

각 시나리오는 사용자 관점의 구체적 상황으로, 가격/기술적 워커의 파이프라인·요구사항이 실제로 동작하는지 검증한다. veriθ 전체 시나리오 중 가격/기술적 워커가 관여하는 부분을 워커 관점으로 상세화한 것이다.

> 이 워커는 단순 지표 나열이 아니라 **국면(regime) 판단 · 신뢰도(confidence) · 리스크 관찰점**까지 산출한다. 단, 이 세 가지는 모두 **결정론적 코드로 확정**되며 LLM은 확정된 값을 문장으로 풀기만 한다. 이 원칙이 지켜지는지가 모든 시나리오의 공통 검증 축이다.

---

## 시나리오 T1 — 해피패스: 종목 차트·국면·기술적 신호 리포트 생성

**상황.** 진수가 2차전지 대표 종목인 LG에너지솔루션을 눌러 "이 종목 차트 흐름 어때?"라고 묻는다. Supervisor가 가격/기술적 워커에 분석을 라우팅한다.

1. 워커가 LLM으로 질문 의도를 해석한다("차트 흐름" → 추세·모멘텀 중심).
2. LLM으로 분석 포커스를 정리한다. 단, 지표를 선택하지 않는다 — 5개 지표는 기본적으로 코드가 고정 계산하고(데이터 부족 시 계산 가능한 지표만 사용), LLM은 설명에서 어떤 관점을 강조할지만 정리한다.
3. `data_collect` 노드가 `cache_service`와 `kis_client`를 통해 일봉·주봉·월봉 캐시를 확인하고, 필요한 타임프레임을 KIS D/W/M으로 조회한다. 과거는 캐시 hit로 재사용하고, 장중엔 오늘 일봉을 우선 갱신한다.
4. 외부 시세는 '데이터'로만 취급한다. 모든 타임프레임 봉 데이터(일봉·주봉·월봉)에 출처·시점 메타데이터를 부착한다.
5. **수집한 일봉·주봉·월봉(모두 KIS 원본)으로 시계열을 구성한다.** 주/월봉은 차트 표시뿐 아니라 분석 입력(상위 타임프레임 추세)으로도 쓰인다.
6. **지표를 타임프레임 역할에 맞게 계산한다(결정론적 코드, LLM 미사용).** 일봉은 기본 5개 지표(이동평균·RSI·거래량·지지저항·패턴) → 신호의 주력(데이터 부족 시 계산 가능한 지표만). 주봉은 추세 방향 + 주요 지지저항. 월봉은 추세 방향만.
7. **국면(regime)을 규칙 테이블로 분류하고 상위 타임프레임으로 보정한다.** ① 일봉으로 1차 국면을 판정한다(우선순위: 과매도 반등 관찰 → 과열 → 상승 전환 관찰 → 상승 추세 유지 → 하락 추세 → 횡보). ② 주봉·월봉 추세로 보정한다 — **이때 `final_regime` 라벨은 6종 그대로 유지하고, 조합 라벨을 새로 만들지 않는다.** 보정 결과는 `alignment_flag`(정합/역행/중립)와 `regime_context`(설명 문구)로 분리해 담는다. 정합/역행은 **방향성 있는 국면**(상승 전환 관찰·상승 추세 유지·하락 추세)에만 적용하고, 과열·과매도·횡보 같은 **중립 국면은 `alignment_flag=중립`**으로 둔 채 맥락만 `regime_context`에 설명한다. 예1(방향성): 일봉 "상승 전환 관찰" + 월봉 "하락" → `final_regime="상승 전환 관찰"`, `alignment_flag=역행`, `regime_context="월봉 추세는 하락으로, 일봉의 긍정 신호는 대세 하락 안의 단기 반등일 수 있습니다."` 예2(중립): 일봉 "과열" + 월봉 "상승" → `final_regime="과열"`, `alignment_flag=중립`, `regime_context="상위 추세는 상승이나 일봉 기준 단기 과열이 관찰됩니다."` ③ 정합/역행 플래그와 함께 최종 라벨을 하나만 확정한다. **보정도 결정론 규칙이며 LLM이 아니라 코드가 라벨을 정한다.**
8. 1차로 지표별 신호(긍정/중립/부정)를 가중 집계해 `signal_score`를 산출한다(코드, 결정론적). 임계값 규칙(|score| ≥ 0.5 명확 / 0.3 ≤ |score| < 0.5 약한 우세 / |score| < 0.3 중립 구간)으로 방향·세기를 정한다.
9. **신뢰도(confidence)를 계산한다.** 지표 일치도·거래량 확인·추세 명확도·신호 충돌 요소로 코드가 산출한다. `signal_score`(방향·세기)와 `confidence`(신뢰도)는 **별개 축**이다.
10. **리스크 관찰점을 도출한다.** 지지·저항·거래량 근처의 관찰 지점을 사실 서술로 정리한다("이탈 시 손절"이 아니라 "이 구간은 신호 강도 판단에 참고 지점").
11. 기간 토글별(3개월/1년/5년) 차트 데이터를 생성하고, 각 차트에 출처·시점 메타를 붙인다.
12. **2차로 LLM이 확정된 regime(멀티프레임 보정 결과 포함)·score·confidence·리스크를 자연어로 해석한다. LLM은 라벨·숫자를 만들지 않고 문장으로 풀기만 한다.**
13. 모든 수치·신호·차트를 출처 시세에 연결해, 차트 데이터 + 신호 종합 + 국면 해석을 Supervisor에 반환한다.

**검증하는 것:** 데이터 수집 → 멀티프레임 계산 → 국면분류·보정 → 종합 → 신뢰도 → 리스크 → 차트 → 해석의 전체 흐름이 끊김 없이 작동하는가. regime·confidence가 코드로 확정되고 LLM은 해석만 하는가. 일봉·주봉·월봉이 KIS D/W/M으로 각각 수집되는가. 멀티프레임 보정이 라벨을 늘리지 않고 alignment_flag·regime_context로 분리되는가. 모든 출력이 출처에 연결되어 검증 게이트를 통과할 수 있는가.

## 시나리오 T2 — 예외 ①: KIS API 장애 (복원력)

**상황.** 진수가 질의한 시점에 KIS API가 일봉·주봉·월봉 중 일부 또는 전체 요청에서 rate limit(429)이나 타임아웃을 반환한다.

1. 워커가 필요한 타임프레임(D/W/M)을 요청하지만 KIS가 429/타임아웃을 반환한다.
2. 지수 백오프(1→2→4초, 최대 3회)로 재시도한다.
3. 재시도가 성공하면 정상 흐름으로 복귀한다.
4. 재시도가 소진되면 폴백한다. 일봉(D) 실패 시 — stale daily 캐시가 있으면 그것으로 계산하고 "최신 시세 미반영" 플래그를 달고(`stale_cache`), 없으면 `data_limited`로 빠진다. 주봉(W)·월봉(M)만 실패한 경우 — stale 상위 타임프레임 캐시가 있으면 사용하고, 없으면 해당 추세를 `unavailable`로 둔 채 일봉 기준 분석은 계속한다(`data_status=data_limited`).
5. **어느 경우에도 빈 곳을 환각으로 메우지 않는다.** stale daily 캐시가 있으면 가능한 범위로 지표를 계산해 부분 결과를 제공하고, 캐시도 없으면 `data_limited`로 안전 착지한다.
6. Supervisor는 멈추지 않고, 제한이 표기된 기술적 분석 결과를 다른 워커 결과와 함께 집계한다.

**검증하는 것:** 외부 의존성이 실패해도 워커가 멈추거나 거짓 데이터를 채우지 않는가. 과거/오늘 분리 덕에 부분 결과라도 정직하게 제공하는가(복원력, 환각 금지).

## 시나리오 T3 — 예외 ②: 데이터가 부족한 종목 (콜드 데이터 → 판단 불가)

**상황.** 신규 상장주라 거래일이 며칠뿐이라, 장기 이동평균(예: 60일선)을 계산할 데이터가 없다.

1. `data_collect`(cache_service·kis_client)는 정상 동작하나 확보된 일봉이 장기 지표 계산에 충분치 않다(예: 상장 7거래일).
2. 워커는 계산 불가능한 지표를 억지로 만들지 않는다. 계산 가능한 단기 지표(예: 5일선)만 산출하고, 장기 지표는 "데이터 부족으로 제외"로 표기한다.
3. 패턴 분석(컵앤핸들 등)도 충분한 기간이 없으면 "판정 불가"로 표시한다.
4. **국면 분류도 봉 수가 부족하면 regime을 억지로 정하지 않고 "판단 불가"로 빠진다(E-2 데이터부족 가드). 이때 confidence는 산출하지 않고, 지표계산·신호 종합·신뢰도·리스크(4·6~8)를 스킵한 뒤 가능한 범위의 차트(9)만 제공한다(국면분류 gate가 지표계산보다 먼저라 지표계산도 스킵 — `trace_schema.md §9.1`).**
5. 단, `regime_unavailable`까지는 아니고 일부 지표만 계산 불가능한 경우에는, 제외된 지표를 가중치에서 빼고 남은 지표로 재정규화한다. "일부 지표 제외됨"을 명시한다.

**검증하는 것:** 데이터가 적을 때 적은 표본으로 과장된 지표·국면을 만들지 않는가. 계산·판단 불가를 환각으로 메우지 않고 정직하게 고지하는가(부분 집계 + 재정규화 + regime 판단 불가).

다만 봉 부족은 일봉뿐 아니라 주/월봉에도 영향을 준다 — 상장 7거래일이면 KIS 주봉도 1~2개뿐이라 월봉 추세는 산출 불가이며, 이 경우 상위 타임프레임 보정 없이 일봉 국면만으로 판정하거나 regime "판단 불가"로 빠진다.

## 시나리오 T4 — 예외 ③: 지표 신호가 엇갈릴 때 (단정 방지)

**상황.** 5개 지표를 계산하니 이동평균·RSI는 긍정, 지지저항은 부정, 거래량·패턴은 중립으로 신호가 갈린다.

1. 1차 가중 집계로 `signal_score`를 산출하니 긍정·부정이 비등해 점수가 0 근처다(|score| < 0.3, 긍정·부정 신호 동시 존재).
2. 단순 다수결로 한쪽을 고르지 않고, 임계값 규칙에 따라 "중립(신호 엇갈림)"으로 판정한다.
3. **confidence도 낮게 산출된다** — 신호 충돌이 커 `conflict_absence` 요소가 낮게 잡히므로, "신뢰도: 낮음·신호 일부 충돌"로 표기된다. (`signal_score`는 방향이 애매하고, `confidence`는 그 판단을 믿기 어렵다는 걸 동시에 보여준다.)
4. 2차 LLM 해석도 단정 표현을 배제하고 "신호 엇갈림·단기 변동성 관찰" 톤으로 작성한다.
5. 각 지표의 개별 신호를 그대로 함께 표기해, 사용자가 어떤 신호가 갈리는지 스스로 판단하게 한다.

**검증하는 것:** 여러 지표 신호가 섞일 때 하나로 뭉개 단정하지 않는가. 애매한 것을 "중립(신호 엇갈림)"으로 정직하게 표시하고 confidence로도 낮게 드러내는가. 추천봇처럼 무조건 긍정/부정을 외치지 않는가.

## 시나리오 T5 — 예외 ④: 계산·규칙 정확성 보장 (결정론·검증 ①②)

**상황.** 같은 종목·같은 시점 데이터로 리포트를 두 번 생성했을 때 지표 값과 regime 라벨이 달라지면 안 된다.

1. 모든 지표 계산은 결정론적 코드로 수행한다. 같은 입력 일봉에는 항상 같은 RSI·이동평균 값이 나온다.
2. **국면 분류도 결정론적 규칙이다. 같은 지표 입력(일봉 + 주/월 추세)에는 항상 같은 최종 regime 라벨(과 alignment_flag)이 나온다.**
3. LLM은 계산·라벨링에 일절 관여하지 않는다. 숫자·라벨을 생성하거나 보정하지 않는다.
4. **D 검증 ① 계산 정확성:** 도구를 mock으로 고정한 결정론적 테스트로, 계산 함수가 정해진 공식대로 동작하는지 CI에서 검증한다(노드 4·5 대상).
5. **D 검증 ② regime 규칙:** "정배열 + RSI 72"가 우선순위 규칙에 따라 "과열"로 분류되는지, **그리고 멀티프레임 보정이 규칙대로 alignment_flag를 정하는지**를 입력→라벨 테스트 케이스로 검증한다(노드 5 대상, 일봉 규칙 + 멀티프레임 보정 규칙 모두). 보정 케이스 예: "일봉 과열 + 월봉 상승" → `final_regime=과열`·`alignment_flag=중립`(중립 국면은 방향성 판정 안 함)·`regime_context` 채움. "일봉 상승 전환 관찰 + 월봉 하락" → `final_regime=상승 전환 관찰`·`alignment_flag=역행`·`regime_context` 채움.
6. trace에 각 지표의 입력·계산 결과·타임프레임별 라벨·최종 regime·신호를 기록해, 사후에 "왜 이 신호·국면인지" 역추적할 수 있게 한다.

**검증하는 것:** 계산과 국면 분류(보정 포함)가 재현 가능한가. LLM이 숫자·라벨을 망치지 않는가. 계산 정확성(①)과 regime 규칙·보정(②)이 테스트로 보장되고 trace로 관측되는가.

## 시나리오 T6 — 예외 ⑤: LLM이 확정 라벨을 왜곡할 때 (검증 ③ · 재생성 루프) [신규]

**상황.** 코드가 regime을 "횡보"로 확정했는데, 2차 해석 LLM이 문장에서 "상승 전환 관찰입니다"라고 국면을 다르게 써버린다. 확정된 라벨과 LLM 출력이 어긋나는 환각 상황이다.

1. 노드 10에서 LLM이 국면 해석 문장을 생성한다.
2. **D 검증 ③ (trajectory eval)가 작동한다** — 코드가 준 라벨(횡보)과 LLM 출력 문장에 담긴 라벨(상승 전환 관찰)이 일치하는지 검사한다.
3. 불일치가 감지되면 **재생성 1회**를 시도한다. 확정 라벨을 프롬프트에 강제 주입해 다시 해석을 생성하고 재검증한다.
4. 재생성 결과가 통과하면 정상 흐름으로 복귀한다.
5. **재생성 후에도 여전히 불일치하면 LLM 문장을 버리고 템플릿 문장으로 폴백한다.** 템플릿은 코드가 확정 라벨·수치로 채운다(예: "현재 국면은 횡보입니다. signal_score는 …, 신뢰도는 …"). 밋밋하더라도 환각보다 정직함을 택한다.
6. 재생성·폴백 여부는 trace에 기록되어, 어떤 리포트가 LLM 원문이고 어떤 것이 템플릿 폴백인지 사후 구분할 수 있다(`interpretation_source`).

**검증하는 것:** LLM이 확정된 라벨을 왜곡했을 때 이를 테스트로 잡아내는가(검증 ③). 재생성 루프가 1회로 제한되어 무한 루프가 없는가. 최종적으로 환각을 통과시키지 않고 템플릿으로 안전하게 착지하는가. **"LLM을 썼지만 검증으로 가뒀다"가 실제로 보장되는가.**

다만 검증 ③은 이제 최종 regime 라벨과 **멀티프레임 보정 결과(alignment_flag·regime_context)**를 함께 검사한다 — 예를 들어 regime이 "상승 전환 관찰"이고 `alignment_flag=역행`(월봉 하락)인데 LLM이 상위 흐름을 누락하고 "상승 전환입니다"로만 단정하면, 확정된 역행 맥락을 빠뜨린 것이므로 이것도 잡아낸다.

또한 검증 ③은 종합 해석(`interpretation`)뿐 아니라 **지표별 설명 문장(`technical_signals[].detail`)도 검사한다.** 코드가 `signal=긍정`으로 확정한 지표를 LLM이 detail에서 부정 뉘앙스로 서술하면 왜곡이다. detail은 종합 해석과 한 번의 LLM 호출로 함께 생성되고 함께 검증되며, 특정 지표의 detail만 실패하면 그 지표의 문장만 코드 템플릿으로 폴백하고 `detail_source="template_fallback"`으로 기록한다(다른 지표·종합 해석은 영향 없음).
